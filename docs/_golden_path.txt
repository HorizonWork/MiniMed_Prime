Luồng hiện tại (khớp spec ở mức cấu trúc)
Entity linker: ScispaCy UMLS + rule-based fallback — khớp §3.1.
Subgraph: 2-hop BFS + PPR top-200, α=0.85 — khớp §3.1 (layer1_retrieval.py:600-663).
PubMed: BM25 0.4 + MedCPT dense 0.3 + cross-encoder 0.3 — khớp §3.1.
Output array: inputs.npy/labels.npy/puzzle_identifiers.npy/dataset.json, L=256, vocab_size=8192, 5 puzzle types — khớp §2.1.2, §2.2.2.
Vấn đề / sai lệch quan trọng so với spec
1. Label gần như trivial — nhánh lỗi nghiêm trọng nhất. trm_dataset_builder.py:88-133: path_to_token_sequence map gold_edge_ids → node_path → lookup trong position_by_node rồi gán labels[pos] = inputs[pos]. Nghĩa là model chỉ học "copy lại token tại vị trí đúng trên sequence đã sort theo PPR". Spec §2.6.2 yêu cầu label là sequence of path tokens gold_path map qua codebook (một chuỗi có trật tự riêng). Hệ quả: TRM học ordering PPR đã có sẵn, không học reasoning.

2. HGT là fallback chứ không phải HGT thật. layer2_embedder.py:252-298 — FallbackHGTLayer là MHA phẳng, không có per-(src_type, edge_type, dst_type) projection. Spec §2.2.1 chỉ định HGT là primary để phân biệt 30 relation type (contraindication vs indication...). Hiện relation chỉ vào qua edge_emb nhưng không modulate attention theo meta-schema.

3. VQ codebook không được pretrain. Spec §2.2.6 yêu cầu pretrain SimpleVectorQuantize trên 50K random subgraph ~1h T4. Code học codebook online cùng TRM → khi build dataset lần đầu, token_id phân bố ngẫu nhiên, mất ổn định giữa các lần build và giữa train/val.

4. Node mất do PPR top-k → gold path bị cắt. Gold edges map về node, rồi chỉ giữ node nằm trong top-200 PPR (§3.1). Nếu node gold không lọt top-200 → vào missing_node_ids, labeled_token_count nhỏ. Nhưng seed_quality.py:48-108 không kiểm labeled_token_count / coverage của gold path trên labels — goldish có thể chứa row mà 0 token được label.

5. Puzzle diversity phụ thuộc entity classifier thô. layer2_embedder.py:42-49 map 5 type, nhưng classify_question_type hiện là rule đơn giản → rất dễ tất cả ví dụ rơi vào 1 type ("other"/"diagnosis"). Spec §2.2.2 coi puzzle_id là điều kiện task — nếu imbalance, 16 token puzzle_emb không đóng vai trò gì.

6. Scispacy-dependency quá cứng. seed_quality.py:95-96: chỉ scispacy_umls là goldish. Nếu cell cài en_core_sci_lg fail trên Kaggle → toàn bộ bị demote silver, goldish rỗng, cell 14 của notebook raise FileNotFoundError. Spec không nói entity linker phải là scispacy_umls; đây là quyết định của code, nên làm soft tier.

7. Notebook dùng limit quá nhỏ. TRAIN_LIMIT=500 / VAL_LIMIT=100 vs spec §2.6.2 khuyến nghị 29K train / 2K val (total 32,682). 500 mẫu không đủ train 7M-param TRM (spec tính ~30K steps × bs 32); bạn sẽ overfit ngay.

8. RELATION_FILTER="" trong notebook. NB3A-Build-Golden-Data.ipynb cell-1 để rỗng → retriever không filter theo question type. Spec §3.1 yêu cầu per-question-type filter (drug_interaction → {drug_drug, contraindication, drug_protein}). Không filter → subgraph noisy, PPR top-200 pha loãng gold edges.

9. Vocab phẳng, không reserved range. Spec §2.2.2: 4K graph + 2K PubMed + 1K reserved + 1K special. Code dùng 1 codebook 4096 duy nhất, trộn node và passage → TRM không phân biệt loại token.

10. LLM-backend reporting không trung thực. Edge mapper auto fail-sang-heuristic nhưng metadata có thể vẫn ghi llm_openai — seed_quality dựa vào backend_used để phân tier (mọi row nhầm là goldish). Cần verify trong medreason_adapter.py đường ghi backend_used sau fallback.

11. Không có NL-provenance trong TRM label. Spec §2.5 coi CoTStep.supporting_pmids là phần của bundle; PubMed passage đã được fuse như "virtual node" (§2.2.5 — bridged trong forward), nhưng labels không bao giờ trỏ tới passage → TRM không học cite PMID. Đây mới là core của "hallucination reduction" ở §1.4.1.
